# w06-routing observations

## Task 1 — Link state by hand
- **Tie-break rule**: when two shortest paths tie, I pick the one whose **first-hop name is alphabetically first** (this falls out naturally from putting `(cost, node, first_hop)` in the heap). A real router does not pick just one; it installs **ECMP**, all equal-cost next hops. In this week's FRR lab too, r1's `172.20.0.0/16` was installed with two next hops (eth0 and eth1).
- `u`'s next hop for `w` is **`x`**. The direct link `u-w` costs 5, but `u-x-y-w` costs 1+1+1 = 3, which is cheaper. Sending it out the `w` interface would mean I looked at adjacency, not routing.
- When `u-x` fails, the next hop for `x, w, y, z` (four destinations) changes from `x` to `v`, and `v` stays as it was because it already went via `v`. In the end `u` sends everything toward `v`.

## Task 2 — Break a real network and time the repair
- **A2** The path to `www.korea.ac.kr` (163.152.6.10) actually does **not leave** campus. Hops 1~2 are private addresses (`172.16.0.2`, `192.168.98.132`); from hop 3, `163.152.233.129`, the addresses are in the university's public block (my own public IP is in this block too). Hops 4~7 are also all `163.152.x.x`, so the path ends inside the university.
- **A3** `www.stanford.edu` goes to a CDN (netlify) so the middle of the path is hidden, so I switched the overseas target to `www.ucla.edu`. Latency is 15~20 ms up to hop 7, then at hop 8 (`10.222.45.47`) it jumps to **about 200 ms**. That single jump looks like the trans-Pacific crossing. However, this carrier's internal addresses (`10.222.x.x`) have no hostnames, so I **could not find which submarine cable** it is from city names. 200 ms is large for a Seoul–US West round trip, and delay from routers slowing down ICMP replies may be mixed in.
- **A4** For `1.1.1.1`, the last hop that answered (hop 12, `141.101.82.12`, in Cloudflare's range) has an RTT of about 8 ms. That is impossible if it were in the US, so the anycast replica must be **nearby, in Korea**. The destination itself did not answer (hops 13~20 are `* * *`), so I do not know whether hop 12 is exactly the last hop.
- **A5** `* * *` has two different causes. One is a **router that does not answer that particular packet**: in the korea.ac.kr trace hop 5 is `* * *` but hops 6 and 7 answer, so traffic is clearly passing through. The other is **ICMP being blocked from that point on**: korea.ac.kr hops 8~20 are all `* * *` even though the site opens, so a firewall is dropping the replies.
- **B2** Each router learned networks it has no direct link to. r1 learned `172.20.0.0/16` (the r2–r3 network) through OSPF, with cost 20 and two paths (eth0, eth1) installed together. That is the protocol working.
- **B4** Cutting the link made all three routers change within **1.2 s**. My polling takes about 1 s to go around the three routers, so the error is ±1 s. This does **not match** the hello 10 s / dead 40 s defaults. r1 noticed the interface going down immediately and flooded a new LSA, and r2 saw that r1's LSA no longer listed it, so it dropped the link without waiting for the dead timer. The dead interval only shows up when **nobody is told about the failure**. So I used `iptables` to block only OSPF on r1's eth1 (link still up), and it took **38.6 s** (first change at 34.4 s). That is under 40 s and consistent with the dead interval; the timer counts from the last hello received, so it comes out a little under 40.
- **B5** Restoring took **16.2 s** (r1 and r3 changed at about 1 s, r2 only at 16.2 s). The router knows the interface is up right away, but to be accepted as a neighbour it has to exchange hellos (every 10 s), exchange databases until it is Full, and only then does the LSA flood and SPF run. When a link goes away, one side only has to learn "it is gone", but when it comes back both sides have to agree again.
- **C3** Raising r1 eth0's cost from 10 to 100 took effect in **1.1 s** (r1's `172.21.0.0/16` switched to going around through eth1 at cost 30). That is almost the same as the link-down case (1.2 s). The difference lies in **the step of noticing the failure**. A cost change only needs the LSA to be flooded, but a failure has to be noticed first. If the interface goes down it is noticed at once, but a silent failure costs the 38.6 s wait.
- Also, `scenario.sh cut` decides the network has reconverged when the whole `show ip route` output changes, but the output contains an uptime counter that changes every second, so it looks like it finished in 1 s. I wrote a separate script that ignores the uptime when comparing. Also, `frrouting/frr:v9.1.0` does not exist on Docker Hub, so I changed the image in `compose.yml` to `v8.4.1`.

## Task 3 — Reconverge without recomputing the world
- **What I keep between events**: each node's shortest cost (`dist`) and which neighbour it hangs from in the tree (`parent`). The first hop is the parent's first hop, so the table is derived from these. Memory is small: two dictionaries proportional to the node count (400) plus a copy of the graph.
- **The three cases**: (1) a link that is on no shortest path and does not create anything shorter is ignored. (2) A link that was used goes down or gets more expensive but **an equal-cost alternative exists**: only the parent changes. (3) A link comes up or gets cheaper and creates a shorter path: I propagate only to **the nodes that get closer** (`_relax_from`). The one case that still forces a full SPF is **losing a link that was in use with no equal-cost alternative**.
- The result is 177 SPF runs instead of 1001 (**82% avoided, strong**), and the table was correct after all 1,000 events. I also checked it with 12 seeds × 2 source nodes. I only added a `with_dist` option to `dijkstra_table()` so that it returns the distances as well, and the incremental propagation in (3) is not a full SPF, so it does not show up in the counter. I am not trying to hide that; it is an incremental SPF that touches only the affected nodes.
- **R5** In wall time the baseline takes 3.3 s and mine takes 4.3 s, so mine is **slower**. A 400-node Dijkstra is already fast in Python, and I do bookkeeping on every event, re-finding parents and rebuilding the first-hop table with `sorted`. It is still **the right choice on a router**. What a router is short of is not memory but CPU at the moment the network is unstable. If a link keeps flapping, SPF runs back to back and clogs the control plane, route updates are delayed meanwhile, and traffic is lost. The memory for keeping the `dist` and `parent` tables is very cheap, and what it saves is the most expensive operation. What Python is short of is interpreter overhead, which is a different problem.
