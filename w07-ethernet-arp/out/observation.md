# w07-ethernet-arp observations

## Task 1 — A learning switch
- **Never back out of the arrival port**: if the destination is on the same port as the sender (e.g. both are behind a hub or another switch, like `C -> A` on port 0 in the check), it has already received the frame on that shared segment. Sending it back out gives it a **duplicate copy**, and for a broadcast or a flood the sender gets **its own frame echoed back**. With two switches connected, each would also bounce every flooded frame back to the other.
- **A switch floods, a router drops**: MAC addresses are flat, so there is no prefix or default route to fall back on. The only way to reach an unknown station is to try every port. That is safe because the flood stays inside one broadcast domain, and the reply teaches the switch where that station is, so the flood happens once. IP addresses are hierarchical: a router that has no route has no "nearby" segment to try, and flooding a packet across the internet would multiply it on every router. So for a router, "unknown" means an error, not "try everywhere".
- **Aging as a timeout**: a station that moves **without sending anything** keeps getting frames sent to its old port until it speaks or the 300 s run out. A station that is alive but quiet is forgotten and starts being flooded again. Time is only a guess at "is this still true?". A more direct signal would be the port going **link-down** (flush every entry on that port at once), a topology change notice (STP shortens aging when the topology changes), or the station announcing itself, e.g. a gratuitous ARP after it moves.

## Task 2 — Watch ARP happen
(Measured on my own laptop as Administrator, Wi-Fi interface `10.233.245.229`, gateway `10.233.245.221`. The clear worked: `arp-cleared.txt` contains only the `224.0.0.22` entry.)
- **A2** The **gateway** (`10.233.245.221`) came back first, and it was the only entry learned by ARP. Both the ping and the HTTPS request to korea.ac.kr go **to the gateway at the link layer**, because neither destination is reachable directly on my subnet. Every packet that leaves the subnet needs the gateway's MAC first. `224.0.0.22` (IGMP) survived the clear because multicast MACs are not learned at all: they are **calculated** from the IP address (`01-00-5e` + the low 23 bits).
- **A3** `before` had 7 entries and `after` has 2 (gateway + `224.0.0.22`). The 5 missing entries are all **static** broadcast/multicast mappings (`.255` subnet broadcast, `224.0.0.251` mDNS, `224.0.0.252` LLMNR, `239.255.255.250` SSDP, `255.255.255.255`). Windows creates them only when it sends to those addresses, and it had not sent anything there in the few seconds before the snapshot. The only dynamic entry, the gateway, is in both tables. So the difference is in which services had recently talked, not in ARP.
- **A4** korea.ac.kr (`163.152.x.x`) is **not in the table**, and neither is any server I visited. ARP only answers "which MAC has this IP **on my own link**". For a remote server my PC looks up the **next hop**, the gateway, and the frame carries the server's IP but the **gateway's MAC**. Each router on the way does its own ARP on its own link. That is why the table stays small however much of the internet I talk to.
- **B2** My request (0.00 s, "who has `.221`? tell `.229`") was sent to **`ff:ff:ff:ff:ff:ff`**, the broadcast address. The gateway's reply (0.03 s) was sent to **my own MAC** (`f4:28:9d:xx:xx:xx`; the last three bytes are replaced with `00:00:00` in the committed capture for privacy), a unicast address.
- **B3** The request reached **every station on the segment**, because I did not know who owned `.221`. That is the whole point of asking. Only the gateway replied. The reply went **only to me**, because the request already told the gateway my IP and MAC (it also learned my address from the request itself). The other three exchanges in the capture (24.7 s, 48.5 s, 72.0 s) were the gateway checking its own entry for me, and those requests were **unicast** to my MAC, not broadcast. Once both sides know each other, nobody else has to hear about it.
- **B4** In the first 60 s of the capture there were **8 ARP frames** (4 request/reply pairs), and only **1 broadcast**. Unicast ARP only costs the two machines involved, but every broadcast is received and processed by every host. If a campus segment has about 500 machines and each sends one ARP broadcast per minute like mine, every host receives ~500 broadcasts/min (~8 per second) and the switches flood each one out of every port. That is still a small amount of bandwidth, but it grows **linearly with the segment size for every single host**, so the total grows roughly with the square. This is why large networks are cut into subnets/VLANs instead of being one flat Ethernet.

## Task 3 — A switch that runs out of room
- **Eviction rule**: least-frequently-used. Every frame that names a MAC (as source or destination) counts as a hit for it. When the table is full, the entry with the fewest hits goes. The evidence I keep is a hit count per table entry, plus a **ghost list** of hit counts for the 64 most recently seen MACs that are *not* in the table, so a station that is evicted and comes back keeps its history. Bookkeeping is bounded at 2 × capacity.
- **Declining admissions**: a new source is admitted only if its hit count is **higher than the victim's**. Otherwise it is declined (its frames still get delivered; only learning it is skipped). I measured each step against the baseline (wasted deliveries, 0 missed in every case): FIFO baseline 323,380 → LRU 218,316 (−32%) → LFU without declining 163,668 (−49.4%) → **LFU + declining 161,920 (−49.9%, strong)**. Most of the gain comes from the eviction rule. Declining only saves another ~1,700 wasted deliveries on this trace, because LFU already evicts the one-time talkers first, so the newcomer and the victim are usually both one-hit stations.
- **R6 — the attack**: an attacker on one port sends a stream of frames with **a new, made-up source MAC in each frame**. Every one is a "new station", so a normal switch learns them all. The table fills with fake entries, and the real stations are evicted. From then on, traffic to the real stations has an unknown destination, so the switch **floods it out of every port, including the attacker's**, and the attacker can read traffic that was never meant for them (this is MAC flooding / CAM table overflow). The switch effectively turns into a hub. My policy blunts the naive version, because one-hit fake MACs are declined. But it has no aging, so an attacker who repeats each fake MAC many times can build up hit counts and **keep** fake entries in the table forever. A better defence is **port security**: limit how many MACs can be learned on one port (or pin them), and shut down or drop on any port that exceeds the limit.
